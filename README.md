# Pathway

Pathway is a learning and simulation management platform. **Educators (admins)** manage learners, create and
assign activities, and follow progress on a live dashboard. **Learners** work through an interactive hardware
troubleshooting simulation, *Diagnose the dead workstation*, where every decision is scored and explained, then
review their results and progress over time.

## Quick start

Requirements: Node.js 22+, a PostgreSQL database on [Neon](https://neon.tech) (free tier is fine).

```bash
npm install                 # also runs `prisma generate`
cp .env.example .env        # then fill in the values (see below)
npm run db:migrate          # creates the tables, using DIRECT_URL
npm run db:seed             # demo data; idempotent, safe to run again
npm run dev                 # http://localhost:3000
```

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | Neon **pooled** connection string, used by the app at runtime |
| `DIRECT_URL` | Neon **direct** connection string, used by Prisma CLI and migrations |
| `AUTH_SECRET` | Signs the session JWT. Generate with `npx auth secret` |
| `SEED_PASSWORD` | Password given to every seeded account (8+ characters) |
| `AUTH_TRUST_HOST` | Only for `next start` outside Vercel; set to `true` |

## Architecture

```
Browser (React client components, TanStack Query)
   │  fetch JSON
   ▼
Route handlers  src/app/api/**/route.ts     auth check → Zod parse → call service → map errors
   │
   ▼
Services        src/server/services/*.ts    business rules, transactions, audit logging
   │                     │
   ▼                     ▼
Prisma (Neon)    Simulation engine  src/lib/simulation   pure TypeScript, no I/O
```

- **Thin route handlers.** Every handler does the same four things: check the role, validate with Zod, call one
  service function, and turn errors into JSON. No database code lives in handlers or components.
- **Services hold the rules** (`learner`, `activity`, `assignment`, `stats`, `simulation`, `learner-portal`,
  `audit`, `auth`). Every change to data writes an audit log entry in the same transaction.
- **The simulation engine is pure.** `engine.ts` has no React, Prisma, clock or randomness; the seed is passed in.
  All fault-specific behaviour is data in `scenarios/hardware-troubleshooting.ts`.
- **Security on the server.** `src/proxy.ts` (Next 16's name for middleware) redirects by role. Each page and API
  also re-checks the role and reloads the user, so a deactivated account loses access at once. Learners can only
  reach their own assignments and attempts; anyone else's return 404.
- **Errors** always have the shape `{ "error": { "code", "message", "fields?" } }`. Unexpected errors are logged on
  the server and returned as a generic 500 with no stack trace.
- **Soft delete.** Deactivating a learner sets their status to `INACTIVE`; nothing is deleted.

```
src/
  app/                 pages (admin/*, learner/*, (auth)/login) and api/* route handlers
  components/          ui/ (shadcn), layout/, admin/, learner/, simulation/
  lib/                 simulation engine + scenario data, Zod schemas, formatting, API client
  server/              db.ts, errors.ts, auth/, services/
prisma/                schema, migrations, seed
tests/                 unit/ (Vitest), e2e/ (Playwright)
```

## The simulation

One of three hidden faults is picked per attempt from a server-generated seed (`faults[seed % 3]`):
**faulty RAM**, **failing power supply** or **CPU overheating**. The learner sees only the symptoms.

- **17 actions** in four groups: Investigate, Safety, Repair, Diagnose.
- **Safety:** any repair before unplugging *and* grounding costs 15 points and is flagged as a static risk.
- **Evidence unlocks actions:** hearing the beep code unlocks *Reseat the RAM*; high BIOS temperatures unlock
  *Inspect the CPU heatsink*; the PSU tester confirms a power fault.
- **Scoring** (configurable in the scenario data): start at 100; repeated investigation −3; skipped safety −15;
  unjustified part swaps −10 to −20; wrong diagnosis −15 with fault-specific feedback; +10 bonus if solved in 6
  actions or fewer; clamped to 0–100.
- **Server is the source of truth.** State is saved after every action, so learners can leave and resume. Each
  request carries the step number it expects; a duplicate or stale submission gets `409`, enforced atomically in
  the database.
- **The fault is never sent to the browser until the attempt is complete**, and is tested for.

## API endpoints

All endpoints return JSON. Errors use `{ error: { code, message, fields? } }` with status 400, 401, 403, 404, 409 or
500.

| Method | Path | Role | Purpose |
| --- | --- | --- | --- |
| `GET`/`POST` | `/api/auth/[...nextauth]` | Public | Auth.js sign-in, sign-out and session |
| `GET` | `/api/stats` | Admin | Dashboard: KPIs, 30-day completions, rate per activity, feed, overdue list |
| `GET` | `/api/stats/me` | Learner | Own progress: stats, score trend, attempt history |
| `GET` | `/api/learners` | Admin | List learners: `search`, `status`, `cohort`, `page`, `pageSize` |
| `POST` | `/api/learners` | Admin | Create a learner (duplicate email returns a field error) |
| `GET` | `/api/learners/:id` | Admin | Learner detail: profile, stats, assignments, attempts with decisions |
| `PATCH` | `/api/learners/:id` | Admin | Edit name, email, cohort; deactivate or reactivate via `status` |
| `GET` | `/api/activities` | Admin | Activities with completion statistics |
| `POST` | `/api/activities` | Admin | Create an activity from a scenario |
| `POST` | `/api/assignments` | Admin | Assign an activity to learners and/or a cohort, optional due date; skips existing |
| `GET` | `/api/assignments/mine` | Learner | Own assignments, "continue" attempt and overall progress |
| `POST` | `/api/simulation/start` | Learner | Start or resume the attempt for one of your assignments |
| `GET` | `/api/simulation/attempts/:attemptId` | Learner (owner) | An attempt; fault revealed only when complete |
| `POST` | `/api/simulation/attempts/:attemptId/actions` | Learner (owner) | Take an action: `{ actionId, expectedStep }` |
| `GET` | `/api/audit` | Admin | Audit log, newest first: `action`, `actor`, `from`, `to`, `page`, `pageSize` |
| `GET` | `/api/reports/learners` | Admin | CSV download: every learner's results, one row per assignment |
| `GET` | `/api/reports/learners/:id` | Admin | CSV download: one learner's report, one row per attempt |

## Dashboard metric definitions

Implemented in `src/server/services/stats.service.ts` and tested in `tests/unit/stats.service.test.ts`.

| Metric | Definition |
| --- | --- |
| **Total learners** | All users with role `LEARNER`, including inactive ones. |
| **Active learners** | Learners with status `ACTIVE`. |
| **Assigned activities** | Number of assignments that belong to active learners. |
| **Completion rate** | Completed assignments ÷ total assignments, counting active learners only, as a whole percentage. With zero assignments it shows "—", never NaN. |
| Completions (30 days) | Assignments completed on each of the last 30 days (UTC days). |
| Rate per activity | Completion rate for each activity, active learners only. |
| Needs attention | Assignments of active learners that are past their due date and not completed. |

## Testing

```bash
npm run typecheck     # Next route types + tsc --noEmit
npm run lint          # ESLint
npm test              # Vitest: 82 tests (engine, services, metrics, CSV, formatting)
npm run test:e2e      # Playwright: 22 tests (needs a seeded database; starts the dev server if needed)
npm run db:clean-tests  # remove any data left by interrupted test runs
```

- **Unit tests** cover the engine (written before it), the scenario catalogue and the error mapping. **Service
  tests** run against the database using uniquely tagged rows that are deleted afterwards, so seed data is never
  touched.
- **End-to-end tests** cover login and role redirects, API access control (403/404/401), a learner completing the
  simulation and the admin seeing the score, an admin adding a learner and assigning the activity through the UI,
  CSV exports, the audit log filters, and an **axe accessibility scan** (WCAG 2.1 A/AA) of every page. Test
  learners are removed automatically after each run.
- Service and end-to-end tests need `DATABASE_URL`, and the end-to-end tests need `SEED_PASSWORD`.

## Deploying to Vercel with Neon

1. **Create the database.** In Neon, create a project and copy two connection strings from *Connection details*:
   the **pooled** string (host contains `-pooler`) and the **direct** string (pooling turned off).
2. **Import the repository** into Vercel (*Add New → Project*). The framework is detected as Next.js and
   `vercel.json` sets the build command to `npm run vercel-build`, which runs
   `prisma generate && prisma migrate deploy && next build`, so migrations are applied on every deploy.
   `vercel.json` also runs functions in `fra1` (Frankfurt); pick the Vercel region closest to your Neon region.
3. **Set environment variables** in *Project → Settings → Environment Variables* (Production and Preview):

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon **pooled** connection string (used by the app at runtime) |
   | `DIRECT_URL` | Neon **direct** connection string (used by `prisma migrate deploy` during the build) |
   | `AUTH_SECRET` | A random secret, e.g. `npx auth secret` or `openssl rand -base64 32` |
   | `SEED_PASSWORD` | Only needed if you run the seed against this database |

   `AUTH_TRUST_HOST` is not needed on Vercel. Set it to `true` only when running `next start` yourself
   (for example a local production check), otherwise Auth.js rejects the host with `UntrustedHost`.
4. **Deploy.** The first build creates the tables.
5. **Seed demo data (optional)** from your machine against the same database:
   `npm run db:seed` with `DATABASE_URL`, `DIRECT_URL` and `SEED_PASSWORD` in your local `.env`.
   The seed is idempotent, so running it again is safe.

Local production check: `npm run build` then `AUTH_TRUST_HOST=true npx next start`.

## Known limitations

- **One scenario.** The engine and data model support more, but only *Diagnose the dead workstation* exists.
  Admins can create several activities from it.
- **One attempt per assignment.** A completed simulation can be reviewed but not retaken.
- **No password reset or invitations.** Admins set a temporary password when adding a learner; there is no email
  system.
- **The assign dialog lists up to 100 active learners.** Assigning by cohort has no limit.
- **Dashboard refresh is polling** (every 10 seconds), not push.
- **Service tests use the real database** (tagged and cleaned up). They need network access to Neon and are slower
  than mocked tests.
- **Dates are bucketed in UTC** on the 30-day chart; a completion near midnight in South Africa (UTC+2) can land on
  the neighbouring day.
- **Due dates are calendar days in UTC.** They display as the day the admin picked, and an assignment becomes
  overdue at the end of that day UTC (01:59 the next morning in South Africa).
